1. Profile、Bundle、Patch

- **Patch** 是对插件 entry 列表的增量操作：插入插件、按 id 修改配置，或禁用已有 entry。
- **Bundle** 是可复用的一组 Patch，例如“基础能力”或“headless 能力”。
- **Profile** 是用户可启动的组合：它选择 Bundle，并用有序名单规定组合顺序，还能附带自己的 Patch。

一次启动可以理解为从空白清单逐层盖章：

```text
空 entry
→ 基础能力 Bundle
→ headless 能力 Bundle
→ Profile 自身 Patch
→ 全局用户 Patch
→ 命令行 --patch
→ 启动器派生覆盖层
```

后层优先。例如基础 Bundle 加入模型和 Session 插件，headless Bundle 加入无界面运行器；用户随后可换模型配置或禁用某个 entry；命令行还能为本次运行临时改写它。

顺序是产品语义，因为 Patch 不只是汇总配置，还会决定“哪些插件实际存在、使用什么配置”。同一个 id 先启用后禁用，与先禁用后重新配置，可能形成不同应用。层级因此表达了明确政策：可复用能力提供默认值，Profile 定义场景，用户和本次启动拥有更高决定权。

2. 服务与 Fiber 的关系

可以沿一条生命周期链理解：

```text
提供服务 → 依赖满足 → 插件启动 → 卸载清理
```

`super(ctx, 'llm')` 发生在服务实例构造时。它通过 `ctx.reflect.provide(...)`，把这个实例以 `llm` 为名字登记到当前作用域；同时把撤销登记的动作交给拥有它的 Fiber。

`ctx.llm` 是消费端取服务的方式。`Context` 是 Proxy，所以这不是普通字段读取，而是进入服务解析器，在当前可见作用域中查找名为 `llm` 的实例。

`inject: ['llm']` 则声明启动条件：“只有 `llm` 服务可用，我才能运行。”它不会把字符串自动变成对象。真正取对象仍通过 `ctx.llm` 等服务解析完成。

Fiber 代表一次插件装载：它跟踪依赖、配置、状态和清理函数。缺少 `llm` 时，依赖该服务的 Fiber 保持 `PENDING`；服务出现后依赖满足，插件才装载。卸载提供者时，其 Fiber 执行清理、撤销服务；相关插件也会按依赖和生命周期退出或等待。Fiber 因而把服务注册、插件存活期和清理责任绑在一起。

3. “Model-visible means logged”

它约束的是：任何具有语义、将进入模型输入的内容，都必须先成为 Session 中的事件事实，不能只放在临时内存缓冲里。反方向不成立：日志可以包含诊断事件，而这些事件未必展示给模型。

Session 的 append-only Event Log 是权威状态；连续 `seq` 给出事实顺序。模型所见对话只是把这些事件折叠后得到的投影，而不是另一份独立真相。

因此 Headless 不直接采用最近一次模型函数返回的字符串。那个返回值可能只是中间结果，之后还可能发生工具调用、追加消息、失败或结束原因变化。Runner 会先记住起始 `seq`，追加用户 follow-up，等待 Agent idle 并 flush，然后扫描本次区间内持久化的 `assistant/message` 与 `turn/end`：输出最后一条 assistant 文本，并按已记录的结束原因决定退出码。这样终端结果、故障恢复和审计看到的是同一组事实。
