不完全是。按 `source.md` 的定义，真正负责“跑起来”的是 `Runner`；`Agent` 更像一份可执行的角色配置。

可以把三者理解成：

```text
Session（跨多次 run 的持久对话历史）
   │
   ├── Run 1：Runner 执行 Agent A → 工具调用 → Agent A → 输出
   │
   └── Run 2：Runner 载入历史 → Agent A → handoff → Agent B → 输出
```

- `Agent`：定义“谁来做”
  - instructions
  - 使用哪个 model
  - 有哪些 tools
  - 能 handoff 给谁
  - 输出类型  
  它本身不执行循环，也不保存完整运行过程。

- `Runner`：定义“怎么跑”
  - 调模型
  - 执行工具并把结果送回模型
  - 判断是否得到最终输出
  - 处理 handoff，切换当前 Agent
  - 应用 guardrail、tracing 和 session 行为  
  所以 Runner 是运行时/调度器，Agent 是被它执行的配置对象。

之所以分开，是因为二者的生命周期和职责不同：同一个 Agent 可以被临时 `run()`，也可以被一个可复用 Runner 执行；一个 Runner 也能在一次循环中先后执行多个 Agent。这样角色定义不会与调度、追踪、状态恢复等基础设施绑死。

`Session` 则放在“跨 Run 的状态层”：

- 一次 `run()` 由 Runner 驱动。
- 一次 run 内可能经历多个 Agent 和多个模型 turn。
- Session 保存多次 run 之间需要延续的对话历史。
- `RunResult` 只是某一次 run 的结果快照，包括最终输出、最后的 Agent、历史和运行状态；它不等于持久 Session。

一句话概括：

> `Agent` 是角色与能力，`Runner` 是执行引擎，`Session` 是跨执行的记忆。

这里最容易误解的是“Agent 在跑模型”：口语上可以这么说，但架构上 Agent 只是告诉 Runner 应该用什么模型、提示词和工具；实际发起模型调用并推进循环的是 Runner。参见 [source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-7s8tqv_1/work/agents-agent-runner-session/source.md)。
