不是“两者都在跑模型”。更准确地说：

- `Agent` 是“怎么做”的定义。
- `Runner` 是“现在开始做，并一直驱动到结束”的执行器。
- `Session` 是跨多次执行保存的对话记忆。

[source.md 第 5–9 行](</private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-7s8tqv_1/work/agents-agent-runner-session/source.md:5>)正是在区分这三层。

```text
Agent：配置 / 角色
  instructions、model、tools、handoffs
                │
                ▼
Runner：执行循环
  调模型 → 执行工具 → 把结果交回模型 → 判断是否结束/移交
                │
                ▼
RunResult：这一次运行的结果

Session：跨多次 run 保存历史
  Run 1 ────────── Run 2 ────────── Run 3
```

假设有一个“客服 Agent”：

```text
Agent
- 指令：帮助用户处理退款
- 模型：某个 GPT 模型
- 工具：查询订单、创建退款
- 可移交给：人工支持 Agent
```

它只是一个配置对象。创建它不会调用模型，类似“菜谱不会自己做菜”。

真正调用模型的是 `Runner`。它负责：

1. 读取当前 Agent 的指令、模型和工具。
2. 组装模型输入并发起调用。
3. 如果模型要求调用工具，就执行工具。
4. 把工具结果送回下一轮模型调用。
5. 如果发生 handoff，就把“当前 Agent”换成另一个 Agent。
6. 得到最终回答后停止。

所以拆开是因为二者变化的维度不同：

- 同一个 `Agent` 可以被执行很多次。
- 同一个 `Runner` 可以执行不同的 Agent。
- Runner 层可以统一处理 tracing、guardrail、模型提供商和工具循环，不必把这些执行机制塞进每个 Agent。
- handoff 时 Agent 会改变，但 Runner 的执行循环仍然是同一个。

`Session` 则不是夹在 Agent 和 Runner 之间的“执行层”，而是与一次 `run` 配合的持久状态：

```text
Session S
├── run("我买了一个键盘")
│   └── Runner 执行 Agent
├── run("它坏了")
│   └── Runner 从 Session 得知“它”指键盘
└── run("帮我退款")
    └── Runner 继续使用此前历史
```

因此可以把关系记成一句话：

> Runner 使用 Agent 的定义执行一次 run，并从 Session 读取、向 Session 写入跨 run 的历史。

还要注意 `Session` 和 `RunResult` 的区别：

- `Session`：跨多次运行延续的历史，生命周期较长。
- `RunResult`：某一次运行产生的输出、最后所在的 Agent、运行状态等，生命周期对应单次 run。

最简心智模型就是：**Agent 是策略，Runner 是控制流，Session 是记忆。**
