因为 **tracing 是记录机制，guardrail 是控制机制**。

可以把 Agent 运行想成开车：

- tracing 像行车记录仪：记录模型生成了什么、调用了哪个工具、发生了什么 handoff。
- guardrail 像刹车和护栏：在不该继续时阻止运行，或让本次执行失败。

关键区别在于时间点和能力：

| | Tracing | Guardrail |
|---|---|---|
| 主要作用 | 观察、审计、排错 | 检查、阻止、约束 |
| 通常何时发挥作用 | 事件发生时留下记录，供事中/事后查看 | 输入、输出或工具调用的边界上 |
| 能否自动阻止危险行为 | 不能 | 能，通过 tripwire 中断运行 |
| 回答的问题 | “刚才发生了什么？” | “这件事是否允许发生？” |

例如，用户要求 Agent 把客户资料发送给外部服务：

- tracing 会记下：模型生成了工具调用、传入了哪些参数、工具返回了什么。
- tool guardrail 可以在工具真正执行前检查参数，发现包含敏感资料后触发 tripwire，阻止调用。

如果只有 tracing，你可能非常清楚地看到事故是怎么发生的，但事故已经发生了。尤其是发送消息、删除数据、付款等具有外部副作用的工具调用，事后可见并不能撤销影响。

`source.md` 里还有一个重要细节：**guardrail 也不一定天然“先拦截”**。并行 input guardrail 为了降低延迟，会和 Agent 工作同时进行；等它触发时，模型可能已经消耗 token，甚至做了一部分工作。真正要求“检查通过之前绝不执行”的场景，应采用串行检查。

因此两者是互补关系：

> Guardrail 决定运行能不能越过边界；tracing 证明运行实际上走过了哪条路径。

而且 guardrail 本身也会产生 trace span，所以 tracing 还能帮助回答：“哪条 guardrail 在什么时候检查了什么，为什么触发或没有触发？”
