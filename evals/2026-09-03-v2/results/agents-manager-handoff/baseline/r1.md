本质差异不是“专家有没有被调用”，而是**谁拥有后续流程的控制权**。

- **专家 Agent 当 tool**：像会独立思考的高级函数。Manager 调它拿结果，随后仍由 Manager 决定是否继续调用其他专家、如何综合，以及最终怎么回复用户。
- **handoff 给专家**：像转接客服。Runner 把当前 Agent 切成专家；接下来的推理、工具调用、再次 handoff 和最终答复，都由专家主导。

可以用一个问题快速判断：

> 专家完成工作以后，结果应该“交回经理加工”，还是专家已经有资格“直接接管并回答”？

| 需求 | 更适合 |
|---|---|
| 查一个专业结论，供主 Agent 组合 | Agent as tool |
| 同时咨询多个专家再综合 | Agent as tool |
| 必须保持统一口吻、统一产品策略 | Agent as tool |
| 用户已经进入一个专业处理流程 | Handoff |
| 专家需要连续追问、调用工具、推进多步任务 | Handoff |
| 后续决策应由专家负责，而不是经理逐项编排 | Handoff |

最容易选错的几种情况：

1. **把“任务很专业”误当成必须 handoff**

   专业程度不是标准。若最终仍需 Manager 权衡多个信息源，例如“让税务、法务、财务分别评估，再给 CEO 一份建议”，专家应当是 tools。

2. **把需要持续交互的专家做成一次性 tool**

   比如退款调查需要专家追问订单号、查系统、判断例外政策。包装成 tool 后，Manager 往往沦为传话筒；这时 handoff 更自然。

3. **过早 handoff，丢掉全局编排**

   用户问“综合技术可行性、成本和风险选方案”，若先交给技术专家，技术专家就成了当前 Agent，未必适合代表所有角色做最终取舍。应由 Manager 调多个专家。

4. **为了统一体验，却 handoff 给风格各异的专家**

   handoff 后最终输出由专家产生。按文中的 guardrail 规则，输出 guardrail 也作用于**最终输出的那个 Agent**，不能想当然地认为 Manager 会回来兜底。

5. **以为 handoff 会永久改变整个会话**

   它首先改变的是当前 `run()` 持续循环中的 current Agent。跨后续 run 如何延续，还涉及 Session、RunResult 中的 last/current Agent，以及应用如何启动下一次运行；Session 保存历史，不等于自动保存“永久路由关系”。

一句话记忆：

> **Tool 是委托工作但不交权；handoff 是连工作台和话筒一起交出去。**
