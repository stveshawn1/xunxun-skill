本质区别不是“都调用了另一个 Agent”，而是**控制权有没有转移**：

- 专家 Agent 当 tool：**委托产出，经理拍板**
- handoff：**委托处理，专家接管**

| 维度 | Agent as tool | Handoff |
|---|---|---|
| 当前负责人 | 始终是 Manager | 切换成专家 Agent |
| 专家完成后 | 结果返回 Manager | 不会自动返回原 Agent |
| 最终回答 | Manager 汇总、改写、负责 | 当前专家直接负责 |
| 适合 | 有边界的子任务、多专家协作 | 整段对话需要另一种能力或身份 |
| 上下文形态 | Manager 决定传什么参数 | 在同一 Runner 循环中继续处理 |
| 用户体验 | 用户一直在和统一入口交流 | 类似被转接到另一个服务台 |

可以用一句判断题：

> 我需要的是专家的“结果”，还是专家来“接手这件事”？

需要结果，就用 tool；需要接手，就 handoff。

### 最容易选错的场景

1. **需要综合多个专家，却用了 handoff**

例如“让财务、法务、技术分别评估，然后给我统一建议”。

这应该是 Manager 把三个 Agent 当 tool，再综合权衡。第一次 handoff 给法务后，法务成了当前 Agent；它并不会天然回到 Manager，也不适合替其他专业做最终汇总。

2. **需要专家持续追问，却用了 tool**

例如复杂故障排查，专家需要连续问用户：

- 什么版本？
- 如何复现？
- 日志是什么？
- 这个实验结果怎样？

如果把专家当 tool，交流会变成“用户 → Manager → 专家 → Manager → 用户”的传话链。容易损失上下文，也让 Manager 成为瓶颈。此时 handoff 更自然。

3. **误以为 handoff 是“调用完自动返回”**

handoff 是状态迁移，不是普通函数调用。专家成为 `current Agent`，除非你明确设计另一次 handoff，否则控制不会自动弹回原 Agent。

如果业务流程要求：

```text
经理 → 专家分析 → 必须回经理审批
```

通常应使用 agent-as-tool，或者显式设计“交回经理”的 handoff；不能指望 Runner 自动返回。

4. **把 tool 当成权限或责任转移**

专家作为 tool 时，面向用户的责任仍在 Manager。专家的语气、输出乃至判断，都只是 Manager 获得的一项工具结果。Manager 仍应检查、组合并生成最终答复。

如果你希望专家的指令、工具集和行为规则成为后续流程的主导，应该 handoff。

5. **忽略 guardrail 的作用位置**

根据 `source.md`：

- Input guardrail 只检查链条中的第一个 Agent；
- Output guardrail 检查最终产生输出的 Agent；
- Tool guardrail 包裹自定义 function-tool 调用。

因此，handoff 后不能假设新专家会自动重新经过初始 input guardrail。若专家有独立的权限或安全边界，需要显式设计检查。反过来，专家作为 tool 时，也要注意其调用是否真正被相应的 tool guardrail 覆盖。

6. **把 handoff 当成持久的会话归属**

handoff 改变的是当前 run 循环里的 `current Agent`。`Session`、`RunResult` 和下一次 `run()` 如何启动是另一层问题。它不等于“以后这个用户永远归该专家”；跨 run 是否延续，需要你的应用根据 run state/current agent 明确处理。

### 一个实用选择法

优先选 agent-as-tool，当你满足任一条件：

- 最终答案需要统一口径；
- 需要调用多个专家；
- 专家任务可以写成清晰的输入、输出；
- Manager 必须审核或整合结果；
- 不希望用户感知内部路由。

优先选 handoff，当你满足任一条件：

- 专家需要直接和用户多轮澄清；
- 后续大部分工作都属于该专家；
- 专家拥有显著不同的工具、身份或操作流程；
- 让 Manager 持续做中间翻译没有价值；
- 产品体验本来就是“分诊后转接”。

最稳妥的默认值是：**边界清楚的子任务先当 tool；只有责任主体确实要改变时才 handoff。**
