本质差异不是“专家能力怎么封装”，而是：**专家拿到的是一项任务，还是整段对话的控制权。**

[source.md 第 7–14 行](</private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/agents-manager-handoff/source.md:7>) 描述了这个控制流：

| | 专家 Agent 作为 tool | Handoff 给专家 Agent |
|---|---|---|
| 专家扮演什么 | 被经理调用的子程序 | 新的对话负责人 |
| 调用后控制权 | 回到经理 Agent | 留在专家 Agent |
| 谁组织最终答案 | 经理 | 专家 |
| 专家产出是什么 | 给经理使用的中间结果 | 直接推进并可能结束当前 run |
| 多专家协作 | 经理可以调用多个专家再综合 | 通常由当前专家继续处理，除非再次 handoff |
| 用户体验 | 始终像在和同一个总负责人交流 | 像被转接到另一个部门 |

可以把它类比成：

- **Agent as tool**：主治医生请放射科会诊。放射科提交报告，主治医生结合其他信息给病人结论。
- **Handoff**：前台确认问题后，把病人转到放射科；接下来由放射科直接问诊和负责。

最实用的判断问题是：

> 专家做完这一步以后，应该由谁决定“下一步做什么”？

- 应该由经理决定 → **作为 tool**
- 应该由专家决定，并继续和用户交互 → **handoff**

你最容易在下面几种情况选错：

1. **因为任务专业，就下意识 handoff**

专业程度不是判断标准。  
例如“查税率”“做一次代码安全检查”“从合同中提取风险点”，即使非常专业，如果结果还要和其他信息组合，专家仍然更适合作为 tool。

2. **经理其实没有能力审查专家，却仍采用 tool**

作为 tool 意味着经理要承担最终综合责任。如果专家返回一份复杂诊断，而经理无法正确解释、追问或判断是否完成，那么经理可能成为“信息损耗层”。这种情况下，让专家直接接管通常更合理。

3. **需要统一答案，却选择 handoff**

例如旅行规划需要分别询问航班、酒店和签证专家，最终还要权衡预算与日期。若直接 handoff 给其中一个专家，它会获得控制权，但未必自然回到总规划者。此时应该由经理把多个专家当 tool 调用后统一决策。

4. **需要持续澄清，却把专家做成一次性 tool**

例如故障排查专家必须连续问用户：

- 哪个环境出错？
- 最近改了什么？
- 能否提供日志？
- 执行检查后结果是什么？

如果每轮都经经理转述，沟通会很笨重，也容易丢失专家的推理脉络。适合 handoff。

5. **误以为 handoff 后经理会自动回来**

handoff 是“更换当前 Agent”，不是临时函数调用。专家成为 continuing loop 中的 current Agent；除非流程中显式设计了交还机制，否则不会自动返回原经理。

6. **忽略安全与校验边界**

两种模式会改变“谁产生最终输出”。文档特别指出：

- 初始输入 guardrail 只作用于链上的第一个 Agent；
- 输出 guardrail 检查最终输出的那个 Agent；
- tool guardrail 包裹的是自定义 function-tool 调用。

所以 handoff 后，不能想当然地认为新专家会重新经过最初的输入检查；而把专家作为 tool 时，也要区分“Agent 工具的结果检查”和普通 function-tool guardrail。

一句话记忆：

> **Tool 是委托工作，handoff 是移交责任。**

如果你关注的是“专家给我什么”，大概率是 tool；如果你关注的是“接下来该由谁主持”，那才是在判断是否 handoff。
