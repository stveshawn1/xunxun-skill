本质差异不是“有没有调用专家”，而是：**专家只提供一次能力，还是接管后续决策权。**

| 维度 | 专家 Agent 当 tool | Handoff 给专家 |
|---|---|---|
| 控制权 | Manager 始终是当前 Agent | 专家成为当前 Agent |
| 专家角色 | 子程序、顾问 | 新负责人 |
| 调用结束后 | 结果返回 Manager | Runner 继续调用专家 |
| 最终答复 | Manager 汇总、统一口径 | 通常由接管后的专家产生 |
| 多专家协作 | Manager 可调用多个专家再综合 | 更像把用户转到一个专业工作台 |
| 对话体验 | 用户一直在和 Manager 对话 | 用户实际上开始和专家对话 |

可以把它们分别理解成：

- **Agent as tool：**“你帮我分析这一块，把结论交给我。”
- **Handoff：**“这个问题现在归你负责，你继续处理。”

例如，用户问：

> 分析这份合同的法律风险，然后给我一份是否签约的综合建议。

如果法律 Agent 是 tool，控制流是：

```text
用户 → Manager → 法律 Agent
                  ↓ 返回风险分析
用户 ← Manager 汇总法律、商业、技术意见
```

Manager 仍然负责“是否签约”这个整体判断。

如果 handoff：

```text
用户 → Manager → 法律 Agent → 后续追问、判断、最终答复
```

此后法律 Agent 成为 Runner 的 current Agent。它不只是提交材料，而是在持续的执行循环里接管问题。

最实用的选择口诀是：

> **缺专业知识，用 tool；该换负责人，用 handoff。**

你最容易选错的地方主要有四种。

1. 把“任务很专业”误认为“应该 handoff”

专业性只说明需要专家能力，不代表需要移交控制权。  
如果最后仍需跨领域整合、保持统一语气或执行全局策略，专家更适合当 tool。

2. 想让专家持续追问，却把它做成 tool

如果专家必须根据用户后续回答不断调整，例如客服排障、税务问诊式信息收集，那么一次工具调用容易变成：

```text
专家提出问题 → Manager 转述 → 用户回答 → Manager 再调用专家
```

Manager 成了低效传话筒。这通常说明应该 handoff。

3. Handoff 之后仍期待 Manager 自动兜底汇总

handoff 会改变 current Agent。Manager 不会天然在最后重新出现。  
如果产品要求“专家分析完，必须回到总控做最终决策”，可以：

- 用 agents-as-tools，让 Manager 从未离开；
- 或明确设计“handoff 回 Manager”的路径。

4. 忽略责任边界随 handoff 一起移动

根据 `source.md`：

- 输入 guardrail 只作用于链路中的第一个 Agent；
- 输出 guardrail 棄查最终产出答案的 Agent；
- handoff 后，最终输出者可能已经变成专家。

所以 handoff 不只是改变提示词或身份标签，它还可能改变：

- 谁决定下一步；
- 谁能调用哪些工具；
- 谁负责最终输出；
- 哪些输出约束会生效。

一个判断题通常就够了：

> 专家完成当前子任务后，我还需要一个上层 Agent 对结果进行取舍、融合或改写吗？

- **需要**：专家当 tool。
- **不需要，希望专家继续直接处理用户**：handoff。

最容易混淆的一点是：两种方式都可能“运行另一个 Agent”，但前者是**嵌套调用并返回结果**，后者是**修改主执行循环的当前负责人**。这才是架构上的本质差异。
