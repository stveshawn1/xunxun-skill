本质差异不是“专家有没有被调用”，而是：**调用后，谁继续拥有这段对话的控制权。**

| 模式 | 专家 Agent 的角色 | 接下来谁决策 | 谁产出最终答案 |
|---|---|---|---|
| Agent as tool | 被经理请来的顾问 | 经理 Agent | 经理汇总后回答 |
| Handoff | 接手案件的新负责人 | 专家 Agent | 专家直接回答 |

这正是 [source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/agents-manager-handoff/source.md:7) 所说的两条 Runner 路径：

- 普通工具调用：结果返回给当前 Agent，下一轮仍由它运行。
- handoff：`current Agent` 被替换，后续循环由专家继续。

可以把它想成：

- **Agent as tool = 主治医生请专科会诊。** 专科医生给意见，主治医生综合检查、病史和其他会诊结果，最后对患者负责。
- **Handoff = 转科。** 病人转到心内科后，心内科医生成为新的主治医生，直接决定后续检查和沟通。

### 最实用的判断问题

不要问“这件事是不是很专业”，而要问：

> **专家完成第一步后，下一轮对话应该由谁决定做什么？**

如果答案是“原来的经理还要比较、验证、组合或统一措辞”，用 **agent as tool**。

如果答案是“从现在开始都属于专家的工作，它应该直接追问用户并完成任务”，用 **handoff**。

例如：

- “分别让法律、财务、技术专家评估，然后给我一个统一方案”  
  → agents as tools。经理必须整合冲突意见。

- “识别出这是退款问题后，转给退款专员继续处理”  
  → handoff。专员应该接管后续问答。

- “让 SQL 专家生成查询，我还要结合业务规则检查并解释结果”  
  → tool。

- “接下来请数据库专家直接跟我排查，可能还需要连续问我日志和表结构”  
  → handoff。

### 最容易选错的几种情况

1. **因为专家能力强就 handoff**

   专业程度和控制权不是一回事。再强的专家，如果只是提供一个局部结论，也应该作为 tool。

2. **需要持续澄清，却把专家做成一次性 tool**

   专家只能把“还需要问用户什么”返回经理，再由经理转述，来回会很笨重。这通常说明专家应该接管，即 handoff。

3. **需要统一裁决，却 handoff 给其中一个专家**

   一旦转交，第一个专家就成为当前 Agent。它不会天然回到经理那里，让经理再比较其他专家。若要回来，必须显式设计“交还”路径。

4. **用了 agent as tool，却原样转发专家答案**

   形式上经理仍在控制，实际上没有验证、融合或统一口径。这样承担了多一层调用成本，却没获得 manager 模式的主要价值。

5. **把 handoff 当成开启一段完全独立的新会话**

   从 [source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/agents-manager-handoff/source.md:14) 的模型看，它是在同一个 Runner 循环中更换当前 Agent，不等于另起一个无关会话。
