`model-visible means logged` 的准确含义是：

> 任何将来会进入模型上下文的语义内容，都必须先成为 Session 事件日志中的正式记录。

这里的 **logged** 不是 `console.log` 或调试日志，而是追加到 Session 的、带连续 `seq` 的事件，例如 `assistant/message`。模型看到的 messages 并不是直接拼接模型 API 返回值，而是从这些已记录的 surface events 重新 fold/projection 出来的。[source.md](</private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/dsh-model-visible-log/source.md:26>)

反过来不一定成立：诊断事件也可以被记录，但 projection 会过滤它们，所以它们不一定对模型可见。

Headless 当然“技术上可以”直接 `print(modelResult)`，但这样会绕过系统的事实来源，产生几个问题：

- 终端显示了回答，Session 却没有它；下一轮模型看不到自己刚才的回答。
- 一次模型调用的返回值不一定是最终用户回答，可能只是工具调用请求或 agent loop 的中间结果。
- middleware、流式合并或后处理后的 `assistant/message` 可能和原始返回字符串不同。
- 无法保证回答与 `turn/end` 已经完整提交，也无法可靠确定退出原因和退出码。
- Headless、交互 UI、重放和恢复会看到不同的会话历史。

因此 Headless 的流程是：

```text
记住起始 seq
  → 提交 user follow-up
  → 等待整个 turn idle
  → flush Session
  → 扫描本轮 seq 区间
  → 取最后一个 assistant/message 打印
  → 根据 turn/end 决定退出码
```

记住起始 `seq` 是为了避免误打印以前轮次的 assistant 消息；等待 idle 和 flush 是为了保证工具循环、最终回答以及结束原因都已落入事件流。

所以这句话表达的是一个架构约束：

> **Session event log 是唯一事实来源。模型可见、用户可见和可重放的内容，都应从这份记录派生。**

不是 Headless 没能力打印刚返回的字符串，而是那个字符串只是内部计算结果；在它成为正式的 `assistant/message` 之前，还不能被当作这个 turn 的权威输出。
