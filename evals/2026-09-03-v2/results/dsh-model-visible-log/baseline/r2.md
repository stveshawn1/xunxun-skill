`model-visible means logged` 的意思是：

> 只要一段语义内容最终能被模型看到，它就必须先成为 Session 中的一条正式事件记录。

这里的 `logged` 不是普通的调试日志，而是写入 Session 的 append-only 事件流。模型的对话上下文并不是从某个临时字符串或内存变量直接拼出来的，而是从这些已记录的 surface events 投影、折叠得到的。

因此关系大致是：

```text
Session 事件流
  ├─ user/message
  ├─ assistant/message
  ├─ tool/...
  └─ turn/end
        ↓ projection / fold
   模型下一轮看到的 messages
```

反过来不一定成立：诊断事件可以被记录，但不一定会进入模型上下文。所以准确说是：

```text
model-visible ⇒ recorded
recorded ⇏ model-visible
```

Headless 不能直接打印模型调用刚返回的字符串，因为那个原始返回值不一定就是系统最终认可的 assistant 输出。模型返回之后，仍可能发生：

- 流式片段合并；
- 工具调用及后续轮次；
- 中间结果被替换或规范化；
- 内容经过插件或 surface 层处理；
- 请求失败、取消或以其他 `turn/end` 原因结束；
- 一个用户请求中产生多个 assistant message。

如果直接打印模型 API 的返回字符串，终端输出就会绕过 Session，形成两个事实来源：

```text
模型调用返回值 ──→ stdout
Session 事件流  ──→ 持久化历史、后续模型上下文、结束状态
```

两者可能不一致。比如模型第一次返回的是工具调用；真正应该打印的自然语言答案，是工具执行后的第二次模型调用产生的。

因此 Headless 的做法是：

1. 记住提交请求前的 Session 序号。
2. 提交 `user` follow-up。
3. 等待整个会话进入 idle。
4. flush Session，确保事件已经落定。
5. 在本次序号区间内查找 `assistant/message` 和 `turn/end`。
6. 打印最后一条正式记录的 assistant 文本。
7. 根据正式记录的结束原因决定退出码。

核心原则就是：**Headless 打印的是会话最终提交的结果，而不是某次底层模型调用的暂时返回值。** 这样终端输出、会话历史、下一轮模型看到的内容以及进程退出状态，才都来自同一个权威事件流。
