这里的 **`model-visible means logged` 不是“模型看到的东西都会打印到控制台”**。这里的 `logged` 指的是：**必须先成为 Session 事件日志中的正式记录**。

更准确的逻辑是：

```text
模型可见的语义内容
        ⇒ 必须有对应的 Session event

有 Session event
        ⇏ 一定对模型可见
```

因为诊断事件也可以进入日志，但不会被投影进模型上下文。[source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/dsh-model-visible-log/source.md:29)

Headless 不直接打印模型调用刚返回的字符串，是因为那个字符串只是**底层模型调用的原始结果**，未必已经成为本轮对外承诺的 assistant 消息。它可能是：

- 一个中间结果，之后还要执行工具并再次调用模型；
- 一次需要重试或被丢弃的结果；
- 流式输出的一部分；
- 工具调用、隐藏内容或无法解析的响应；
- 已生成但尚未成功提交到 Session 的内容；
- 在后续处理过程中被规范化或替换的内容。

因此，系统把 Session event log 当作唯一事实来源：

```text
模型返回
  → runtime 解释和处理
  → 记录 assistant/message
  → 记录 turn/end
  → flush 持久化
  → Headless 从本轮 seq 区间读取并打印
```

Headless 会先记下起始 `seq`，提交用户消息，等待系统 idle，再 flush，然后只扫描本轮区间内的 `assistant/message` 和 `turn/end`：最后一个 assistant 消息决定 stdout，结束原因决定退出码。[source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/dsh-model-visible-log/source.md:30)

所以“不能直接打印”主要是架构约束，并非技术上 `console.log()` 做不到。直接打印会制造两个事实来源：

1. 终端说模型回答了 X；
2. Session 里却可能没有 X，或者最终记录的是 Y。

这样 replay、恢复、审计、模型上下文重建以及退出码判断都会互相矛盾。简言之：

> Headless 打印的是“已经提交成功的会话输出”，不是“某次模型请求碰巧返回的字节”。
