这里的 **`model-visible means logged`** 更准确地说是：

> 任何会进入模型上下文、影响模型下一步判断的语义内容，都必须先成为 Session 中的一条正式事件。

这里的 `logged` 不是“打印到调试日志”，而是“记录进 Session 的追加式事件流”。反过来并不成立：诊断日志可以被记录，但不一定会展示给模型。[source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/dsh-model-visible-log/source.md:28)

可以把它理解成：

```text
Session 事件流（事实来源）
        │
        ├──折叠/投影──> 模型看到的 messages
        │
        └──筛选──────> Headless 最终打印的结果
```

例如，助手最终说了“任务完成”，Session 中应该存在类似：

```text
seq=42  assistant/message  "任务完成"
seq=43  turn/end           reason=completed
```

下一轮给模型构造上下文时，从这些事件重新生成消息，而不是依赖某次函数调用暂存在内存里的返回字符串。

Headless 不能“直接打印模型调用刚返回的字符串”，这里的“不能”主要是**架构契约上的不能**，不是技术上做不到。因为模型 API 的原始返回值不一定等于这一轮正式对外公布的助手消息：

- 它可能只是中间步骤，随后还要执行工具并再次调用模型。
- 一轮可能发生多次模型调用，不能随便把其中一次当作最终答案。
- 调用可能被重试、取消或最终以错误结束。
- 返回内容可能先经过转换，再形成正式的 `assistant/message`。
- 即使拿到了文本，也不能仅凭它判断整轮成功、失败还是被中断；这要看 `turn/end`。

如果 Headless 直接打印原始字符串，就会出现两个互相矛盾的真相：

```text
终端说：模型回答了 X
Session 说：没有 X，或者本轮最终失败了
```

之后恢复会话、重放、审计或生成下一轮模型上下文时，`X` 都不存在。终端用户却已经看到了它。

所以 Headless 被刻意设计成普通的 Session 消费者：

1. 记住开始时的 `seq`，避免捡到以前的答案。
2. 提交用户消息。
3. 等这一轮所有异步工作结束。
4. `flush`，确保事件已经完整写入。
5. 只扫描本轮区间中的 `assistant/message` 和 `turn/end`。
6. 打印最后一条正式助手消息，并根据正式结束原因决定退出码。[source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/dsh-model-visible-log/source.md:30)

一句话概括：**Headless 打印的是“Session 已经承认的最终结果”，而不是“模型客户端刚好吐出来的一段字符串”。** 这样终端输出、会话历史和模型下一轮看到的内容才来自同一个事实来源。
