`model-visible means logged` 的准确意思是：

> 任何会进入模型上下文的语义内容，都必须先有一条对应的 Session 事件记录。

这里的 `logged` 不是“打印到控制台”，而是“写入 Session 的追加式事件日志”。

可以把 Session 看成权威流水账，模型看到的消息列表只是从这本账中折叠出来的一个视图：

```text
Session 事件
  ├─ user/message
  ├─ assistant/message
  ├─ tool/result
  └─ diagnostic/...
          │
          ▼
筛选、折叠
          │
          ▼
下一次模型调用的 messages
```

需要注意，这句话是单向约束：

- 模型可见 ⇒ 一定有事件记录
- 有事件记录 ⇏ 一定模型可见

例如诊断事件可以被记录下来，但不会进入模型上下文。

Headless 不能直接打印“模型调用刚返回的字符串”，是因为那个返回值不是系统的权威最终输出。它只是模型调用层内部的临时结果。之后还可能发生：

- 流式响应尚未完整结束；
- 内容被转换或过滤；
- 本次调用其实是工具调用，不是最终答复；
- 调用被取消、重试或替代；
- 一个 turn 中发生多次模型调用；
- 文本还没有成功提交成 `assistant/message`；
- turn 最终以错误或其他原因结束。

如果 Headless 直接打印这个临时字符串，就可能出现：

```text
终端打印了 A
Session 实际记录了 B
下一轮模型看到的也是 B
```

这样控制台输出、持久状态和模型上下文就分裂了，而且重放 Session 时无法解释“当时为什么输出了 A”。

所以 Headless 走的是 Session 边界，而不是模型调用边界：

1. 记住开始时的 `seq`。
2. 提交用户消息。
3. 等待系统进入 idle。
4. flush Session，确保事件已经落定。
5. 扫描这段序号区间里的 `assistant/message` 和 `turn/end`。
6. 打印最后一条已记录的 assistant 文本。
7. 根据已记录的结束原因设置退出码。

一句话概括：

> Headless 打印的不是“模型曾经吐出了什么”，而是“系统最终承认并记录了什么”。

这也是 `model-visible means logged` 的设计价值：Session 是唯一事实来源；模型上下文、Headless 输出和事后重放都由同一份事实派生。
