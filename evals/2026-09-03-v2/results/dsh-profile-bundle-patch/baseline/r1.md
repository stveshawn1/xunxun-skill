可以这样区分：

| 概念 | 本质 | 磁盘上的形态 | 是运行时对象吗？ |
|---|---|---|---|
| **Profile** | 一套启动配置的入口/组合方案 | 一个目录，包含 `package.json` 和自己的 `cordis.patch.yml` | 不是 |
| **Bundle** | 可复用、可分发的配置层 | 一个 npm 包；其 manifest 指向一个 Patch 文件 | 不是 |
| **Patch** | 对插件条目列表的声明式修改 | 通常是 YAML 文件；加载后会变成内存中的配置数据 | 本身不是插件实例 |

它们的关系大致是：

```text
Profile
├── package.json
│   └── dsh.profile.bundles: [Bundle A, Bundle B, ...]
└── cordis.patch.yml          ← Profile 自己的 Patch

Bundle A（npm 包）
└── manifest 指向 cordis.patch.yml
```

启动时，DSH 从空的插件条目列表开始，依次合并：

```text
Bundle A Patch
→ Bundle B Patch
→ Profile Patch
→ Home Patch
→ 命令行覆盖
→ Launcher 覆盖
```

越靠后的层优先级越高。Patch 可以：

- 插入新的插件条目；
- 按 `id` 修改已有条目的配置；
- 禁用某个条目。

真正的运行时对象是在最终配置合成以后才产生的：

```text
Profile / Bundle / Patch
        ↓ 配置合成
最终插件条目列表
        ↓ Cordis 应用插件
Fiber + 插件实例 + Service + Context
```

所以最简洁的记忆方式是：

- **Profile 是“这次怎么组装”**
- **Bundle 是“可复用的配置包”**
- **Patch 是“具体怎么改配置的文件”**
- **Fiber、Service、插件实例才是运行中的对象**
