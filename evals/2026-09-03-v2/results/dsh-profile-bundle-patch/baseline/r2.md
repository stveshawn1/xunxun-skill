它们主要都是“启动配置层”，不是运行中的对象。区别在于：

| 概念 | 磁盘上的形态 | 作用 | 是否是运行时对象 |
|---|---|---|---|
| **Profile** | 一个目录，包含 `package.json` 和自己的 `cordis.patch.yml` | 选择一组 Bundle，并定义 Profile 级覆盖 | 否 |
| **Bundle** | 一个 npm 包；其 `package.json` 指向一个 Patch 文件 | 封装一组可复用的插件配置 | 否 |
| **Patch** | 通常是 YAML 配置文件，也可理解为解析后的补丁数据 | 添加插件项、按 ID 修改配置或禁用插件 | 否 |

关系可以简化成：

```text
Profile 目录
├── package.json
│   └── dsh.profile.bundles: [Bundle A, Bundle B, ...]
└── cordis.patch.yml              ← Profile Patch

Bundle（npm 包）
├── package.json
│   └── 指向 Patch 文件
└── xxx.patch.yml                 ← Bundle Patch
```

启动时，DSH 从空插件列表开始，依次合并：

```text
Bundle patches（按声明顺序）
→ Profile patch
→ Home patch
→ 命令行 overlays
→ Launcher overlays
```

越靠后的层优先级越高。因此：

- Profile 是“启动方案/装配入口”。
- Bundle 是“可复用、可安装的配置包”。
- Patch 是“实际描述增删改的配置补丁”。

真正运行起来后，Patch 中的插件条目才会被 Cordis 应用。每次插件应用对应一个运行时 **Fiber**；插件提供的能力可能成为运行时 **Service**。所以不要把 Profile、Bundle 或 Patch 本身当成 Fiber、Service 或插件实例。

一句话记忆：

> **Profile 选 Bundle，Bundle 携带 Patch，Patch 最终生成插件运行实例。**
