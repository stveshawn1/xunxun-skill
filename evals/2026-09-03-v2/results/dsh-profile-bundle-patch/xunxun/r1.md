可以先记成一句话：

**Profile 是目录级配置，Bundle 是 npm 包，Patch 是配置文件里的“修改说明”；它们都不是 Cordis 里运行中的服务对象。**

| 概念 | 磁盘上的形态 | 在 DSH 中的角色 |
|---|---|---|
| Profile | 一个目录，包含 `package.json` 和自己的 `cordis.patch.yml` | 描述一次启动要采用哪些 Bundle，以及 Profile 自己的定制 |
| Bundle | 一个 npm package | 提供一层可复用的 Patch；包的 manifest 指向 Patch 文件 |
| Patch | 通常是 YAML 文件；读取后变成内存中的配置数据 | 对插件条目执行插入、修改或禁用 |

可以把它们想成：

```text
Profile（整套启动方案）
├── package.json
│   └── dsh.profile.bundles:
│       ├── Bundle A ──> patch A
│       └── Bundle B ──> patch B
└── cordis.patch.yml    ← Profile 自己的 patch
```

启动时，DSH 从空的插件条目列表开始，依次叠加：

```text
空列表
  → Bundle A 的 Patch
  → Bundle B 的 Patch
  → Profile 自己的 Patch
  → Home Patch
  → 命令行覆盖
  → Launcher 覆盖
```

越靠后的层优先级越高。

因此更精确地说：

- **Profile 不是单个文件，也不是运行中的实例**，而是以目录为载体的一套启动配置。
- **Bundle 确实是包**，具体是 npm package；它的主要作用是分发一层 Patch。
- **Patch 在磁盘上通常是文件，在读入后是普通配置数据**。它会被组合算法消费，但不是像 `Service`、`Context` 或 `Fiber` 那样有生命周期的运行时对象。
- 真正的运行时对象，是 Patch 最终促成创建的插件应用、`Fiber`、服务实例等。

一个非常实用的区分是：

> **Profile 决定“选哪些层”，Bundle负责“包装和分发某一层”，Patch描述“这一层具体改什么”。**
