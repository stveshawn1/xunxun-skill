它们都不是“运行中的对象”。三者处在启动配置层，只是封装层级不同：

| 名称 | 本质 | 磁盘上的形态 |
|---|---|---|
| Profile | 一套完整的启动配置入口 | 一个目录 |
| Bundle | 可复用、可安装的配置模块 | 一个 npm 包 |
| Patch | 对插件列表进行修改的声明 | 通常是 `cordis.patch.yml` 文件 |

关系可以这样记：

```text
Profile
├── package.json
│   └── 按顺序引用多个 Bundle
├── cordis.patch.yml          ← Profile 自己的 Patch
│
Bundle（npm 包）
└── package.json
    └── 指向该 Bundle 的 Patch 文件
```

启动时，DSH 并不是把 Profile、Bundle、Patch 分别实例化成对象，而是依次读取并合并这些 Patch：

```text
空插件列表
  → Bundle 1 的 Patch
  → Bundle 2 的 Patch
  → Profile 的 Patch
  → Home Patch
  → 命令行覆盖
  → Launcher 覆盖
  → 最终插件配置
```

越靠后的层优先级越高。Patch 能做的事情主要是：

- 插入一个插件条目；
- 根据条目 `id` 修改配置；
- 禁用条目。

最终插件真正被应用后，才进入运行时对象层：Cordis 会为每次插件应用建立一个 `Fiber`，由它持有依赖状态、校验后的配置、生命周期副作用和清理逻辑；插件提供的服务也会成为运行时服务对象。

所以最短的记法是：

> Profile 是“整套方案目录”，Bundle 是“可复用的 npm 配置包”，Patch 是“修改插件配置的声明”；三者共同生成配置，`Fiber` 和 Service 才是运行中的对象。
