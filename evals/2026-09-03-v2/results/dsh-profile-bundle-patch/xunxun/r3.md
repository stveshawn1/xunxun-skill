最准确的分类是：

| 概念 | 磁盘上的形态 | 逻辑作用 | 是运行中的对象吗？ |
|---|---|---|---|
| **Profile** | 一个目录 | 描述一次完整启动配置：选择哪些 Bundle，并提供自己的 Patch | 不是 |
| **Bundle** | 一个 npm 包 | 提供一组可复用的配置层；包清单指向它的 Patch | 不是 |
| **Patch** | 通常是 `cordis.patch.yml` 配置文件 | 对插件条目进行新增、修改或禁用 | 不是；加载后会变成内存数据 |

可以把三者理解为：

```text
Profile（整套启动方案）
├── package.json
│   └── dsh.profile.bundles: [Bundle A, Bundle B, ...]
└── cordis.patch.yml         ← Profile 自己的 Patch

Bundle（可复用 npm 包）
└── package.json
    └── 指向 Bundle 自己的 Patch
```

启动时，DSH 从空的插件条目列表开始，依次叠加：

```text
Bundle Patch（按 Profile 中的顺序）
→ Profile Patch
→ Home Patch
→ 命令行覆盖
→ Launcher 覆盖
```

越靠后的层优先级越高。这正是 [source.md](</private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-c5rsc611/work/dsh-profile-bundle-patch/source.md:7>) 描述的组合过程。

关键区别是：

- **Profile 和 Bundle 是配置的组织、分发单位。**
- **Patch 是实际修改配置的指令层。**
- 它们共同计算出最终的“插件条目列表”。
- 插件真正启动后，Cordis 才会为每次插件应用创建运行时的 **Fiber**；Fiber 才是拥有依赖、校验后配置、生命周期副作用和清理逻辑的运行中对象。

一句话记忆：

> **Profile 选套餐，Bundle 装模块，Patch 做改动，Fiber 才在运行。**
