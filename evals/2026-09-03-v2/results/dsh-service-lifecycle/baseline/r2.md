关键点是：`ctx` 不是普通对象，而是一个 `Proxy`。`super(ctx, 'llm')` 也不是简单地执行 `ctx.llm = this`，而是把服务实例注册进 Cordis 的服务注册表。

大致链路如下：

```text
new LLMService(ctx)
  ↓
super(ctx, 'llm')
  ↓
ctx.reflect.provide('llm', 当前实例)
  ↓
服务注册表保存：'llm' → 当前实例
  ↓
读取 ctx.llm 时，Context Proxy 去注册表解析
```

`Service` 的构造函数实际上做的是：

```ts
constructor(ctx: Context, name: string) {
  this.ctx = ctx
  this.name = name

  ctx.reflect.provide(name, this, this[Service.check])
}
```

所以：

```ts
super(ctx, 'llm')
```

相当于声明：

> 当前这个对象就是名为 `llm` 的服务实现。

而 `Context` 构造时返回了一个 Proxy：

```ts
const self = new Proxy(this, ReflectService.handler)
```

当代码读取：

```ts
ctx.llm
```

如果 `llm` 不是 `ctx` 自身的普通字段，Proxy 的 `get` trap 就会去服务注册表中查找 `llm` 对应的实例。相关实现见 [Context Proxy](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/cordis/src/reflect.ts) 和 [Service 构造函数](https://github.com/deepseek-ai/deepseek-harness/blob/master/vendor/cordis/src/service.ts)。

`inject: ['llm']` 做的是另一件事：声明消费方的运行时依赖。

```ts
export const inject = ['llm']

export function apply(ctx: Context) {
  ctx.llm.generate(...)
}
```

它的含义不是“把字符串转换成对象”，而是：

1. 告诉 Cordis：这个插件必须依赖 `llm`。
2. 如果 `llm` 尚未可用，该插件保持 `PENDING`，不执行 `apply` 或构造函数。
3. `llm` 可用后，Cordis 才启动这个插件，并把对应实现记录到消费方 Fiber 的依赖快照中。
4. 此时 Proxy 读取 `ctx.llm`，就能从该 Fiber 已声明的依赖里找到实例。
5. 如果 `llm` 提供方之后卸载，消费方也会自动卸载；服务恢复后，消费方重新启动。

也就是说，三件事各管一层：

| 机制 | 作用 |
|---|---|
| `super(ctx, 'llm')` | 在运行时提供、注册 `llm` 服务 |
| `inject: ['llm']` | 声明消费依赖，控制插件启停，并授权直接读取 |
| `declare module ... Context { llm: ... }` | 只负责 TypeScript 类型提示和类型检查 |

还有一个容易忽略的细节：插件里直接写 `ctx.llm`，原则上需要声明 `inject`。Proxy 的实现明确准备了 `cannot get property "llm" without inject` 这个错误。若想做可选查询，可以不声明依赖，而是写：

```ts
const llm = ctx.get('llm')

if (llm) {
  // 当前存在才使用
}
```

所以一句话总结：

> `super(ctx, 'llm')` 是“我提供 llm”；`inject: ['llm']` 是“我必须依赖 llm”；`ctx.llm` 则是 Proxy 根据当前插件的依赖和作用域动态解析出来的服务实例。
