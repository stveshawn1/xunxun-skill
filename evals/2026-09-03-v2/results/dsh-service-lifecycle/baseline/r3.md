核心是两套机制配合：`Service` 负责注册，`Context` 的 `Proxy` 负责读取。

```ts
class LLM extends Service {
  constructor(ctx: Context) {
    super(ctx, 'llm')
  }
}
```

`super(ctx, 'llm')` 最终执行：

```ts
ctx.reflect.provide('llm', self, ...)
```

相当于把当前服务实例登记进 Context 的服务容器：

```text
服务名 "llm" → LLM 实例
```

它并不是直接执行：

```ts
ctx.llm = self
```

但 `ctx` 是一个 `Proxy`。访问：

```ts
ctx.llm
```

时，代理的属性读取逻辑会发现 `llm` 不是 Context 自身的普通属性，于是转去服务容器解析 `"llm"`，最后返回之前注册的 LLM 实例。相关线索见 [source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-_l_n37_8/work/dsh-service-lifecycle/source.md:15)。

可以近似理解为：

```ts
const ctx = new Proxy(context, {
  get(target, key) {
    if (key in target) return target[key]
    return serviceRegistry.resolve(key)
  },
})
```

而：

```ts
inject: ['llm']
```

表达的是插件的依赖关系：“这个插件运行必须有 `llm` 服务”。它不会创建 `ctx.llm`，也不会把字符串转换成 LLM 对象。

它主要影响生命周期：

```text
LLM 插件启动
  ↓ provide('llm', instance)
服务可用
  ↓
依赖 inject: ['llm'] 的插件可以启动
  ↓
插件运行时通过 ctx.llm 解析实例
```

如果 `llm` 尚未提供，依赖插件不会正常激活；如果提供者被卸载，Cordis 也能按照依赖关系清理或暂停消费者，而不是让消费者继续持有失效服务。

所以两者分工是：

- `super(ctx, 'llm')`：我是服务提供者，把实例注册为 `"llm"`。
- `ctx.llm`：通过 Context 代理查找 `"llm"`。
- `inject: ['llm']`：我是服务消费者，声明自己依赖 `"llm"`，让框架管理启动顺序和生命周期。

即使不写 `inject`，只要服务碰巧已经存在，`ctx.llm` 在运行时可能仍能读到；但框架不知道这是正式依赖，无法保证启动顺序和卸载安全。TypeScript 是否认可 `ctx.llm`，则通常还需要给 `Context` 做接口扩展，这和运行时注册是另一回事。
