关键是：`super(ctx, 'llm')` 在运行时把当前服务实例注册进 `ctx` 的服务容器；`ctx.llm` 是 `Context` 的 `Proxy` 动态解析出来的，并不是普通赋值产生的属性。

链路可以还原成：

```ts
class LLMService extends Service {
  constructor(ctx) {
    super(ctx, 'llm')
  }
}
```

父类构造器里执行了：

```ts
ctx.reflect.provide('llm', self, check)
```

它相当于告诉 Cordis：

> 在当前插件生命周期内，服务名 `llm` 对应这个实例。

随后别的插件访问：

```ts
ctx.llm
```

因为 `ctx` 是一个 `Proxy`，属性读取会被拦截。读取 `"llm"` 时，Cordis 会去服务注册表中查找当前上下文可见的 `llm` 实例并返回它。因此它大致等价于：

```ts
ctx.llm
// 概念上相当于
ctx.reflect.resolve('llm')
```

注意，它不是简单的：

```ts
ctx.llm = this
```

两者的区别是，Cordis 的服务注册还与插件的作用域、启动顺序和销毁生命周期绑定。提供服务的插件被卸载时，对应注册也能被清理。

`inject: ['llm']` 是消费方的依赖声明，例如：

```ts
export const inject = ['llm']

export function apply(ctx) {
  ctx.llm.chat(...)
}
```

它告诉框架：

> 这个插件必须依赖名为 `llm` 的服务。

Cordis 会把这项依赖记录到当前插件的 Fiber——即这次插件运行所对应的生命周期对象中。这样框架可以：

- 等 `llm` 服务可用后再启动插件；
- 在服务缺失时，不直接运行这个插件；
- 在服务消失或重新提供时，停止或重新处理依赖它的插件；
- 把依赖关系纳入统一的清理和生命周期管理。

所以三者分别负责不同事情：

| 写法 | 角色 | 作用 |
|---|---|---|
| `super(ctx, 'llm')` | 服务提供方 | 注册名为 `llm` 的实例 |
| `ctx.llm` | 服务消费方 | 从当前上下文动态解析该实例 |
| `inject: ['llm']` | 依赖声明 | 告诉框架此插件运行前必须具备 `llm` |

最容易混淆的一点是：`inject: ['llm']` **不会把字符串转换成对象，也不负责创建 `ctx.llm`**。真正提供对象的是 `provide()`；`inject` 只是声明“没有它我不能运行”。

可以把整个过程压缩成：

```text
LLM 插件启动
  → super(ctx, 'llm')
  → provide('llm', 实例)
  → 服务进入注册表
  → 依赖 llm 的插件满足 inject 条件
  → 插件运行
  → ctx.llm 经 Proxy 查表得到实例
```

这也解释了为什么服务名必须一致：注册的是 `'llm'`，依赖声明和属性访问就都使用 `llm`。参见 [source.md](/private/var/folders/sz/cc03_p510f55yvxmgytgww9r0000gn/T/xunxun-v2-7s8tqv_1/work/dsh-service-lifecycle/source.md:15)。
