核心是：`'llm'` 被当成服务名注册进 `Context` 的服务容器，而 `ctx` 又是一个 `Proxy`。所以 `ctx.llm` 实际是在按名字查询服务，并不是普通对象属性。

提供服务时：

```ts
class LLMService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'llm')
  }
}
```

`super(ctx, 'llm')` 最终执行的是：

```ts
ctx.reflect.provide('llm', serviceInstance, ...)
```

也就是建立映射：

```text
服务名 "llm" ──> 当前 LLMService 实例
```

之后别的插件读取：

```ts
ctx.llm
```

因为 `Context` 是 `Proxy`，属性读取会被拦截，近似于：

```ts
ctx.llm
// 等价思路：
ctx.reflect.get('llm')
```

所以中间并没有真正执行过：

```ts
ctx.llm = instance
```

`inject: ['llm']` 是另一件事：声明插件依赖 `llm` 服务。

```ts
export const inject = ['llm']

export function apply(ctx: Context) {
  ctx.llm.doSomething()
}
```

它是在告诉 Cordis：

> 这个插件只有在 `llm` 服务可用时才具备运行条件。

Cordis 的 Fiber 会记录和检查这项依赖，并把它纳入插件生命周期管理。可以把三者区分为：

| 代码 | 作用 |
|---|---|
| `super(ctx, 'llm')` | 注册、提供 `llm` 服务 |
| `ctx.llm` | 查询并取得已经注册的服务实例 |
| `inject: ['llm']` | 声明当前插件必须依赖该服务 |

因此，`inject` 并不会把字符串变成对象，也不是它创建了 `ctx.llm`。真正使 `ctx.llm` 在运行时可读取的是 `provide('llm', instance)` 加上 `Context` 的 Proxy 查询机制；`inject` 负责的是依赖检查与生命周期协调。

还有一个容易混淆的层次：TypeScript 是否允许你写 `ctx.llm`，属于编译期类型问题，通常由 `Context` 的接口扩展解决；运行时能否拿到实例，则由上述注册和解析机制决定。
