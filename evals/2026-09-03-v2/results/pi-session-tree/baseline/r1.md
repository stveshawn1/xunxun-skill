对，JSONL 物理上仍然只是一行一行追加。Pi 的“分叉”不是把文件分成两段，而是通过每行的 `id` 和 `parentId` 在追加日志上建立一棵逻辑树。

比如文件依次写入：

```jsonl
{"type":"session","version":2}
{"type":"message","id":"a","parentId":null,"role":"user","content":"设计登录功能"}
{"type":"message","id":"b","parentId":"a","role":"assistant","content":"方案一"}
{"type":"message","id":"c","parentId":"b","role":"user","content":"继续实现"}
{"type":"message","id":"d","parentId":"b","role":"user","content":"换成无密码登录"}
{"type":"message","id":"e","parentId":"d","role":"assistant","content":"方案二"}
```

物理写入顺序是：

```text
a → b → c → d → e
```

但 `parentId` 表达出来的逻辑结构是：

```text
a
└── b
    ├── c
    └── d
        └── e
```

关键在第四条消息 `d`：

- 它确实写在 `c` 后面；
- 但它的 `parentId` 不是 `c`，而是更早的 `b`；
- 所以它成为从 `b` 分出的另一条支线。

当 Pi 选择叶节点 `e` 加载上下文时，它不会把前面的所有物理行都交给模型，而是沿父指针向上回溯：

```text
e ← d ← b ← a
```

反转后得到当前对话：

```text
a → b → d → e
```

`c` 虽然仍然保存在同一个 JSONL 文件中，但不属于当前分支，因此不会进入这次模型上下文。

所以可以把它理解成：

> JSONL 是 append-only 的事件存储；`id` / `parentId` 是覆盖在事件存储之上的树结构。

类似 Git：commit 对象可以按时间不断创建，但每个 commit 指向自己的父 commit；新 commit 也可以指向较早的 commit，从而形成分支，并不需要回头修改旧记录。
