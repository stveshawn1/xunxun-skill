对，JSONL 在物理上仍然只是不断向文件末尾追加。Pi 的“分叉”是通过每行里的 `id` 和 `parentId` 表达的，而不是在文件中间插入内容。

例如文件按时间追加成这样：

```jsonl
{"type":"message","id":"A","parentId":null,"role":"user","content":"写个排序函数"}
{"type":"message","id":"B","parentId":"A","role":"assistant","content":"方案一"}
{"type":"message","id":"C","parentId":"B","role":"user","content":"继续优化"}
{"type":"message","id":"D","parentId":"A","role":"assistant","content":"换成方案二"}
{"type":"message","id":"E","parentId":"D","role":"user","content":"继续这个方案"}
```

物理顺序是一条追加日志：

```text
A → B → C → D → E
```

但根据 `parentId` 重建出来的是一棵树：

```text
A
├── B
│   └── C
└── D
    └── E
```

当你回到 `A` 再生成一个回答时，Pi 不会删除或改写 `B`、`C`，而是在文件末尾追加 `D`，并让 `D.parentId = A`。这就形成了新分支。

加载对话时，Pi 也不会把所有物理行都交给模型，而是从当前选中的叶节点沿 `parentId` 向上追溯：

- 选中 `C`：模型看到 `A → B → C`
- 选中 `E`：模型看到 `A → D → E`

所以可以把它理解成：

> JSONL 的行序表示“节点创建时间”，`parentId` 表示“对话结构”。

这与 Git 很像：对象可以按任意物理顺序存放，真正的历史关系由父指针决定。分叉并不要求文件本身分叉。
